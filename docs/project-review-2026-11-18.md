# 全项目审查 · 2026-11-18

以下为 2026-11-18 审查时的代码状态与复现记录。六项问题的后续修复见[开发记录](CHANGELOG.md#2026-11-19--修复全项目审查发现的六项问题)。

## 1. P1：新工具出图后，继续普通修改被附件用途校验拦住

- 触发：从换色、扩图、抠图或有参考图的单张入口上传新图片，生成完成后，在工作台继续普通修改、蒙版编辑或扩图；上传图未通过对话另行标记用途。
- 影响：返回 409，要求说明“产品图还是参考图”，无 Agent 工具链路无法顺畅连续编辑。明确的同款换色分支不在此阻断范围内。
- 原因：`src/lib/direct-image-generation.ts:26` 复用上传函数，上传函数写入对话附件但不标记用途；`src/lib/studio-main.ts:172` 调用 `studioEditReferences`，最终 `src/lib/conversation-images.ts:45` 只忽略当前生成结果 ID，原始上传图仍被 `requireResolvedImages`（第 17 行）判为未解决。
- 复现：隔离账号真实上传到本地数据库和存储后，未解决附件数为 1；调用实际引用解析函数，以不同的结果图 ID 模拟继续编辑，稳定得到上述错误。未运行生图模型；结果图 ID 仅用于测试引用门禁，不冒充完整真实生成验收。
- 建议：独立工具上传不要产生未分类的对话附件副作用，或让直接编辑使用其已冻结的输入用途；保留普通 Agent 对话的用途检查。

## 2. P1：普通产品的改图任务失败后无法重试

- 触发：普通产品图的修改任务失败，点击重试。这里指非 `generationMode=direct` 的改图。
- 影响：接口返回“只能重试当前图包尚未重试的失败候选图”，原编辑参数无法通过此入口重试。
- 原因：`src/lib/studio-main.ts:158` 创建 `logicalModel=edit` 任务时没有 `batchId`；`src/app/api/studio/[id]/route.ts:55` 仅为 direct 任务分流，其余转到 `quoteBatch`；`src/lib/image-packs.ts:87` 强制要求旧任务有 `batchId`。
- 复现：在隔离数据中建立失败的普通编辑任务，实际调用 `quoteBatch`，得到同一拒绝。未入队、未调用模型。
- 建议：增加普通编辑任务重试路径，重放原图、描述、模型、蒙版或扩图范围等冻结输入，沿用额度、幂等及队列；不要把编辑任务伪装成整套候选图。

## 3. P1：账单同步异常可以终止整个 worker

- 触发：配置 ZenMux 后，定时账单同步读取数据库遇到连接异常。
- 影响：当前 Node 运行配置下出现未捕获 Promise 拒绝，worker 退出；前端仍可打开，但后台生成处理可能中断。
- 原因：`scripts/kie-worker.ts:39` 对 `reconcileZenMuxCosts()` 只有 `finally`，没有 `catch`；`src/lib/zenmux-billing.ts:25` 的初始数据库读取在逐条异常处理之外。
- 复现：提取实际定时器代码，在隔离子进程注入数据库异常，确认退出码 1。没有中断正在运行的数据库或 worker。
- 建议：捕获并记录同步异常，下轮再试，保证账单补查失败不会终止生图任务进程。

## 4. P2：新工具刷新后丢失上传图片和操作草稿

- 触发：在 `/tools/recolor` 等页面上传图片、填写参数后刷新。
- 影响：原图预览、产品关联和输入描述消失，用户需要重新选择；服务器已创建的项目仍存在。扩图范围等状态同样没有恢复机制。
- 原因：`src/components/design-preview/image-tool-page.tsx:33` 起的产品 ID、图片、描述、环境、范围等仅在组件状态中；URL 不保存项目或草稿标识。
- 复现：真实组件、模拟接口的浏览器测试上传图片并填写“黑色木纹”，刷新后预览及描述为空，URL 仍无项目标识。浏览器直接验证了图片和描述丢失，其他状态缺乏持久化由代码确认。
- 建议：按账号和工具保存草稿，通过 URL 恢复已上传项目，并恢复未确认提交的请求编号，避免刷新后重复创建或提交。

## 5. P2：首次上传响应丢失后重试会创建重复项目

- 触发：服务器已完成首次上传，但浏览器未收到响应；用户重试上传同一文件。
- 影响：重复创建“自由生图”项目及素材，列表出现重复项。
- 原因：`src/components/design-preview/image-tool-page.tsx:49` 首次上传不带产品 ID，也不带上传幂等号；产品 ID 只在成功收到响应后保存（第 52 行）。`src/lib/direct-image-generation.ts:24` 每次无产品 ID 的调用都新建随机项目。
- 复现：隔离账号以同一文件连续调用实际首次上传函数，两次生成不同项目。结合客户端响应丢失后的状态处理确认该重试路径；没有模拟断开生产网络。
- 建议：同一次上传尝试保存稳定请求编号，服务端返回既有完成结果；有意新建的另一项目仍应允许使用相同文件，不能单靠文件哈希全局去重。

## 6. P2：带 EXIF 方向的照片扩图坐标不一致

- 触发：上传带旋转方向元数据的手机照片，然后按浏览器显示范围扩图。
- 影响：视觉上有效的范围被服务端拒绝；前后处理使用不同方向，也存在原图覆盖方向不一致的风险。本轮确认的是尺寸校验拒绝，未调用模型验证最终图片。
- 原因：`src/lib/storage.ts:28` 保存原始宽高；`src/components/design-preview/expand-editor.tsx:25` 使用浏览器自动旋转后的自然宽高；`src/lib/expanded-edit.ts:5` 又使用未经方向归一的原图尺寸。
- 复现：合成 600×400、orientation=6 的 JPEG。服务端记录 600×400，浏览器显示 400×600；500×650、偏移 (50,25) 的扩图范围适用于显示尺寸，却被原始尺寸校验拒绝。
- 建议：上传时统一像素方向和尺寸；扩图、蒙版及原图覆盖采用同一坐标系，并兼容已存储的历史照片。
