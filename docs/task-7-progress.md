## 四个 bug：原因与修复方案（本阶段不修）

### 1. 正式档案第 2 版，但 Agent 理解度 0%、全部缺失

**原因已确认：产品级正式档案与使用者级会话草稿混用了展示口径。**

`src/lib/agent-state.ts` 的 `agentSession()` 按 `productId_createdById` 创建 / 查找会话，新会话直接使用 `emptyProfile()`。`agentSnapshot()` 只解析这个会话的 `profileDraft` 并计算理解度，没有读取产品最新正式 ProductProfile。正式档案保存在产品级，确认操作只回写执行确认的那个会话。

对目标 SKU 的只读核对结果：正式档案已到第 2 版；两版按现有算法都是 **86%**。原验收会话有已确认档案、理解度 86%；当前管理员对应另一个空会话，未关联正式档案、理解度 0%。因此有正式档案与看到 0% 同时发生，并非正式档案丢失。已确认也不等于所有字段都已确认：现有理解度按 7 个必填字段中 `confirmed` 的比例计算，推测字段不计满分。

**建议修复：**统一 SKU 顶栏与档案抽屉的产品级数据来源，优先显示最新正式档案及其理解度；会话草稿单独标为“正在补充 / 待确认”。没有正式档案时才用草稿；解析失败要提示，不能默默降为全部缺失。新资料引起草稿变化时保留正式档案展示，同时明确“有新资料待核对”。不得仅为补展示而自动设置 `confirmedProfileId`、确认方案或跳过费用 / 风险保护。

**后续验证：**同一 SKU 换账号、刷新、新会话、补资料、修改草稿及正式第 2 版都应显示正确来源；推测、缺失、冲突仍保留，付费前的确认规则不放松。

### 2. 已产生费用，但“本次会话”是 $0.000000

**原因已确认：费用按本人会话汇总，用户看到的却是整个 SKU 的已有创作。**

`agentSnapshot()` 的 LlmCall 与 GenerationJob 都按当前 `session.id` 查询；`agent-workspace.tsx` 将两项相加后 `toFixed(6)`。只读核对中，管理员空会话没有任何 LLM / 生图账目，因此这个会话确实合计为 0。原验收会话有 66 条 LLM 调用、10 条生图任务，记录合计分别为 `$1.310837` 与 `$0.250000`；这些数含既有预估记录，不能称为全部已核实实际账单。另有 9 条历史生图任务没有 sessionId，也不会进入任何本人会话合计。

**建议修复：**明确拆开“这个 SKU 的累计花费”“本人本次会话”“本月用量”。顶部采用与 SKU 工作台范围匹配的 SKU 累计花费，详情再看本人会话及分类；产品级汇总纳入旧的未关联会话任务并避免重复计数。区分实际、预估、预留与待核对，展示最多 2 位小数；非零但不足 $0.01 时显示“小于 $0.01”。不要把其他人的账目硬改成当前会话费用，也不要为修显示篡改历史 sessionId。

**后续验证：**跨账号、空会话、有费用会话、历史未关联记录、生成进行中预留、失败 / 未知扣费与账单回填都能解释金额来源；与现有配额账本一致。

### 3. 实拍参考显示 5/3

**原因已确认：两个入口采用不同约束，却共用同一 Asset 集合。**

原 `PhotoManager` / photos 上传入口要求最多 3 张实拍；但 `uploadProductDocuments()` 可收集资料图片，`classifyDocument()` 将图片直接改为 `Asset.type = photo`，没有应用同样的数量限制。真实验收为已有 2 张实拍加新上传的 3 张，共 5 张。`productSnapshot()` 读全部有效 photo，PhotoManager 把总数与固定分母 3 拼起来，因此出现 5/3。

实际生成准备仍按实拍排序取最多 3 张，**收集数量 5 不等于向模型发送 5 张**。这是素材集合、生成选择与旧 UI 限额之间的规则不一致。

**建议修复：**明确区分“已收集实拍”与“本次生成选用”。推荐保留资料，不删除现有图片：档案显示“已收集 5 张，本次选用 3 张”，显式选择 / 排序最多 3 张用于新任务；服务端统一验证生成选择，前端显示选中数量。若最终业务规则仍要求最多保存 3 张，则所有上传 / 分类入口在同一产品锁事务统一校验，并向用户提供选择保留的入口，不自动删除现有 5 张。

**后续验证：**资料上传、图片分类、旧上传入口、并发上传与重新排序一致；场景生成最多 3 张实拍，编辑为原候选 + 最多 3 张实拍；旧任务冻结参考不被破坏。

### 4. “部分候选图基于旧版特征生成”未指明图片或处理方式

**原因已确认：当前代码仅计算全局布尔值。**

`image-pack-board.tsx` 使用两层 `.some()` 判断成功任务是否有图片、`job.input.identityVersionId` 是否不同于当前身份版本。结果只有 `old: boolean`，随后显示一句全局提示；没有保留受影响图片列表，也没有逐图标签、变更摘要或处理操作。历史缺少身份快照时，还可能把“未知”直接当成“旧版”。

**建议修复：**在快照中按候选资源返回新旧 / 未知状态及所属图位；在具体候选上标“档案已更新 · 待核对”。详情抽屉显示本张使用的产品依据、最新变化与“对照后保留 / 按最新档案重新生成”；缺少历史信息时显示“依据未知，需要核对”。重新生成必须走原有报价与用户确认，并保留旧候选、父图关系与已选终稿，禁止自动重做、扣费或覆盖。技术版本号只在详情的技术记录中展示。

**后续验证：**明确区分当前、旧版与未知候选；人工图位无 AI 快照不误报；多个候选、旧终稿与隐藏图片处理正确；每张告警都能定位并给出处理入口。
